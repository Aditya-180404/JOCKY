User's intended product direction:
- JOCKEY is an offline-first defensive forensic DSL, compiler, native runtime, and local reporting tool.
- The website should let users write and validate JOCKEY source, compile/download an OS-specific artifact, download the local compiler, read setup guides, documentation, examples, and playbooks.
- A user runs the downloaded executable/binary on their own target OS. The binary collects local evidence and creates evidence.json plus evidence.json.meta.json.
- Evidence verification and report generation should happen locally through the CLI, not by uploading evidence to the website.
- No login or registration is required for now.
- The user wants a simple Docker command to start the website/compiler service.
- The user wants a temporarily permissive .gitignore to make team collaboration easy, then plans to tighten it later.

Audit conclusions already established:
- The DSL compiler path is real: lexer -> parser/AST -> semantic IR -> HIR -> MIR -> programmatic LLVM -> native runtime.
- Linux x86_64 compilation was tested successfully. A native ELF was built and executed; it collected real evidence. Deep SHA-256/Merkle verification passed, and a tampered copy failed verification.
- Windows x86_64 is declared but was not verified. ARM64 is explicitly unsupported.
- The old web product was designed as an authenticated cloud management platform with tools, investigations, evidence upload/storage, MinIO, PostgreSQL, Redis, and a compiler worker. That scope does not match the user's intended product.
- Earlier web execution used to fabricate evidence; current compiler_service.rs was improved to label results REAL or COLLECTOR_FAILED, but it still executes collectors in the API process and must not be described as a sandbox.
- The DSL operation collect timeline is incorrectly lowered to CollectSystemInfo in compiler/hir/src/lib.rs. This remains a real defect.
- CLI report generation already exists for terminal, markdown, and JSON. Reports should be local derived outputs; canonical evidence should remain JSON plus metadata sidecar.
- Docker/API/packaging contain old TRACEFORGE names and currently need repair.

Important implementation constraints:
- Preserve compiler/runtime code rather than rewriting it.
- Do not add AV evasion, EDR disabling, BYOVD exploitation, covert networking, credential theft, persistence, or any other offensive capability.
- Do not claim that a server process, timeout, or temporary directory is a secure sandbox.
- Do not silently fabricate evidence. Collection errors must remain explicit.
- Do not delete old cloud-platform source immediately. It can remain un-routed while the team completes the product refocus.
